# 5. 실습과 자동화

## Miniconda 컨테이너 실습 정리

강의 실습은 Miniconda가 포함된 Linux 이미지를 받아 컨테이너에서 셸을 열고, 호스트 폴더를 공유해 Python 파일을 실행하는 흐름입니다.

```bash
docker pull continuumio/miniconda3
docker image ls
docker run -it -v /c/rokey:/rokey continuumio/miniconda3 /bin/bash
```

컨테이너 내부에서 공유 폴더로 이동해 파일을 만들고 실행합니다.

```bash
cd /rokey
python hello.py
exit
```

강의에선 `/f/rokey` 형식 경로를 썼다. 경로는 내 Windows 폴더와 터미널에 맞춰 바꾼다. 컨테이너를 종료한 뒤에는 `docker ps -a`로 목록을 확인할 수 있고, 이름 변경·재시작은 다음처럼 할 수 있습니다.

```bash
docker rename <기존이름> linux
docker start linux
docker exec -it linux /bin/bash
```

실습에서 `docker attach`를 쓰기도 하지만, 실행 중 컨테이너에서 별도 셸을 여는 목적에는 `docker exec -it`가 일반적으로 더 안전하고 다루기 쉽습니다.

## 반복 작업 자동화

Docker를 자동화에 활용하면 이미지 빌드와 컨테이너 실행을 같은 절차로 반복할 수 있습니다. Dockerfile은 빌드 절차를, Compose 파일은 여러 서비스의 실행 설정을 코드로 기록합니다.

### Docker Compose

Compose는 웹 애플리케이션과 데이터베이스처럼 함께 필요한 여러 컨테이너의 설정을 한 파일로 관리합니다.

```yaml
services:
  web:
    build: .
    ports:
      - "3000:3000"
    depends_on:
      - db
  db:
    image: postgres:16
    environment:
      POSTGRES_DB: app
      POSTGRES_USER: app
      POSTGRES_PASSWORD: local-example-only
    volumes:
      - db-data:/var/lib/postgresql/data
volumes:
  db-data:
```

```bash
docker compose up --build -d
docker compose ps
docker compose logs -f
docker compose down
```

예시 암호는 로컬 학습용입니다. 실제 비밀번호를 파일이나 이미지에 평문으로 저장하지 말고 안전한 비밀 관리 방식을 사용합니다. `depends_on`은 시작 순서를 지정하지만, 의존 서비스가 요청을 받을 준비가 끝났는지까지 보장하지 않을 수 있습니다.

## CI/CD 파이프라인

- **CI(지속적 통합)**: 코드 변경마다 자동 빌드, 테스트, 검사 수행
- **CD(지속적 전달/배포)**: 검증된 버전을 배포 준비하거나 자동으로 배포

일반 흐름:

```text
코드 변경 → 테스트 → 이미지 빌드 → 버전 태그 → 레지스트리 푸시
→ 배포 환경에서 이미지 적용 → 헬스 체크
```

테스트가 실패하면 배포를 중단하고, 이미지 버전을 명확히 기록해 문제 시 이전 버전으로 되돌릴 수 있게 합니다.

## 운영 체크리스트

- 불필요한 파일과 비밀 정보가 이미지에 포함되지 않았는가?
- 이미지 버전을 식별할 수 있고 같은 버전을 다시 배포할 수 있는가?
- 컨테이너 로그와 상태를 확인할 방법이 있는가?
- 데이터가 컨테이너 삭제와 함께 사라지지 않도록 저장소를 분리했는가?
- 공개 포트와 컨테이너 권한을 필요한 범위로 제한했는가?
- 배포 실패 시 이전 이미지로 복구할 수 있는가?
