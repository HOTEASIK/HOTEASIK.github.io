# 통신 방식 비교

## 정의·핵심
- **ROS2 노드끼리 말하는 길은 셋, 설정 하나** (기초 4·5차시)
  - **토픽** = 방송: 계속 흘려보내고, 듣고 싶은 사람이 듣는다.
  - **서비스** = 전화: 한 번 묻고 답을 기다린다.
  - **액션** = 택배: 주문하고, 중간 알림을 받고, 취소할 수 있다.
  - **파라미터** = 다이얼: 통신이 아니라 노드의 설정값.
- **고르는 질문 순서**: ① 계속 흐르는 데이터인가? → 토픽. ② 한 번 묻고 바로 답을 받나? → 서비스. ③ 오래 걸리고 진행 상황·취소가 필요한가? → 액션. ④ 실행 중 바뀔 수 있는 설정인가? → 파라미터.
- **흔한 실수 둘**: 오래 걸리는 일을 서비스로(클라이언트가 멈춘다) / 한 번 정할 설정을 토픽으로 반복 송신.
- **비율**: 실제 ROS 코드의 약 70%가 토픽 — 대부분은 「계속 흐르는 데이터」다.

## 원리·구조
| | 토픽 | 서비스 | 액션 | 파라미터 |
|---|---|---|---|---|
| 방향 | 단방향 | 요청↔응답 | 목표→피드백→결과 | 읽기/쓰기 |
| 동기 | 비동기 | 동기(기다림) | 비동기+진행 보고 | — |
| 연결 | 1:N, N:N | 1:1(서버 하나) | 1:1(서버 하나) | 노드 소속 |
| 취소 | — | 불가 | 가능 | — |
| turtlesim 예 | `/turtle1/cmd_vel`, `/pose` | `/spawn`, `/set_pen` | `/rotate_absolute` | `background_b` |
| 로봇 예 | 라이다, 영상, 속도 | 지도 저장, 모드 전환 | 목표 지점 이동 | 최대 속도 |
| CLI | `ros2 topic` | `ros2 service` | `ros2 action` | `ros2 param` |

## 코드 예시
```python
# 상황 → 통신 방식 고르기
def choose(streaming=False, needs_reply=False, long_running=False, config=False):
    if config: return "파라미터"
    if streaming: return "토픽"
    if long_running: return "액션"
    if needs_reply: return "서비스"
    return "토픽"
cases = {"라이다 스캔 10Hz": dict(streaming=True),
         "지도 저장해 줘": dict(needs_reply=True),
         "주방까지 가 줘": dict(needs_reply=True, long_running=True),
         "최대 속도 0.5": dict(config=True)}
for k, v in cases.items(): print(k, "→", choose(**v))
# 라이다 스캔 10Hz → 토픽 / 지도 저장해 줘 → 서비스 / 주방까지 가 줘 → 액션 / 최대 속도 0.5 → 파라미터
```

#### 통신 선택

| 분류         | 토픽 (Topic)                | 서비스 (Service)       | 액션 (Action)                        | 파라미터 (Parameter)     |
| :--------- | :------------------------ | :------------------ | :--------------------------------- | :------------------- |
| **데이터 성질** | 끊임없이 계속 흐름                | 단발성으로 한 번 오감        | 처리하는 데 시간이 오래 걸림                   | 거의 바뀌지 않고 유지됨        |
| **응답 방식**  | 없음 (그냥 흘려보냄)              | 즉시 응답               | 진행 상황(피드백) + 최종 결과                 | 설정 읽기 / 쓰기 응답        |
| **통신 방향**  | 일방향                       | 요청자 → 응답자           | 요청자 \(\leftrightarrow\) 실행자 (양방향)  | 노드 내부 (외부 제어 가능)     |
| **관계**     | N:N (서로 누군지 모름)           | 1:1 (응답을 기다림)       | 1:1 (진행 상황을 보고함)                   | 노드 고유의 속성            |
| **실패 알림**  | 없음                        | 응답 칸 (`ok` 등으로 확인)  | 종결 도장(Status) + 최종 결과 칸            | 설정 변경 거부 (콜백 거부)     |
| **상태 위치**  | 받는 쪽 `self` (최신값 유지)      | 보통 없음 (휘발성)         | `execute` 함수 안 (작업 수명 주기)          | 노드 자체의 `self`        |
| **확인 명령**  | `ros2 topic info/echo/hz` | `ros2 service call` | `ros2 action send_goal --feedback` | `ros2 param get/set` |
| **직관적 비유** | 라디오 방송                    | 전화 통화               | 택배 배송 추적                           | 설정 손잡이 (다이얼)         |

##### 요약
1. **토픽 (Topic)**: 센서 데이터처럼 **주기적이고 끊임없이 흐르는 정보**에 적합합니다.
2. **서비스 (Service)**: 상태 확인이나 일회성 계산 요청처럼 **단발성 대답이 필요할 때** 사용합니다.
3. **액션 (Action)**: 로봇의 이동이나 정밀 제어처럼 **오래 걸리는 작업을 감시하고 취소해야 할 때** 필수적입니다.
4. **파라미터 (Parameter)**: 로봇의 최대 속도 제한이나 센서 포트 설정처럼 **코드 변경 없이 다이얼을 돌리듯 값을 바꿀 때** 활용합니다.

### 잘못 고르면 생기는 일
  

| 잘못된 선택                 | 결과                                 |
| ---------------------- | ---------------------------------- |
| 순찰(액션)을 서비스로           | 진행 상황을 볼 수 없고, 취소할 수 없고, 클라이언트가 묶임 |
| 상태(파라미터)를 서비스로         | 누가 물어야만 알 수 있음                     |
| 명령(서비스)을 토픽으로          | 받았는지 확인할 응답이 없음                    |
| 긴 작업(액션)을 서비스로         | 클라이언트가 막히고 타임아웃                    |
| 한 번이면 될 설정(파라미터)을 토픽으로 | 같은 값을 반복 전송해 자원 낭비                 |
