# 소켓의 한계와 ROS

## 정의·핵심
- **정의**: 소켓으로 직접 통신을 짜면서 사람이 떠안은 **"손이 간 일 여섯"** 과, ROS가 그것을 어떻게 대신하는지의 정리 (기초 2차시 → 기초 3차시).
- **손이 간 일 여섯** — 다섯 단계를 지나며 쌓인 건 기능이 아니라 손이 가는 일이었다.
  1. IP와 포트를 양쪽이 똑같이 맞췄다 (① 한 마디 주고받기)
  2. 서버를 반드시 먼저 켰다 (① 일부러 막혀보기)
  3. while 루프와 끊김 처리를 직접 짰다 (② 계속 주고받기)
  4. 직렬화 규칙을 손으로 정했다 (③ 포장하고 해체하기)
  5. 클라이언트가 둘 이상이면 연결을 일일이 관리했다 (④ 배선이 늘어난다)
  6. 약속이 한쪽만 어긋나도 통신이 깨졌다 (⑤ 깨뜨려보기)
- **한 뿌리**: 여섯 가지는 따로 노는 게 아니라 "통신은 양쪽의 약속을 **사람이 직접** 맞춰야 성립한다"는 한 뿌리에서 나왔다. 코드가 붙을수록 불어나고 틀릴 자리도 함께 는다.
- **ROS가 맡으면**: 우리는 **이름만 정한다**. 기초 3차시에 ROS를 깔고 talker·listener를 띄워 "IP를 적었나요? 포트는요?" — 아무것도 안 적었는데 통한다는 걸 확인한다.

## 원리·구조
| 손이 간 일 | 소켓 | ROS2 |
|---|---|---|
| 상대 찾기 | IP·포트 손으로 | DDS 자동 발견, 토픽 이름만 |
| 켜는 순서 | 서버 먼저 | 상관없음 |
| 연결·끊김 관리 | while·break·try | 자동(재연결 포함) |
| 직렬화 | 콤마·encode 손으로 | .msg 타입으로 자동 |
| 1:N 배선 | 연결마다 열고 닫기 | 같은 토픽 구독만 |
| 언어 맞추기 | 양쪽 규칙 일치 | C++·Python 섞어도 됨 |

## 코드 예시
```python
# 같은 '1:N 방송'을 직접 배선 vs 이름 기반 버스로 비교 (ROS 토픽의 발상)
from collections import defaultdict
nodes = [f"n{i}" for i in range(10)]
direct = sum(1 for i in range(len(nodes)) for j in range(i + 1, len(nodes)))
print("직접 배선 연결 수:", direct)        # 직접 배선 연결 수: 45

bus = defaultdict(list)                    # 토픽 이름 → 구독 콜백들
for n in nodes[1:]:
    bus["/chatter"].append(lambda m, n=n: f"{n}:{m}")
got = [cb("hello") for cb in bus["/chatter"]]   # 발행 한 번이면 모두에게
print(len(got), got[0])                    # 9 n1:hello
```
