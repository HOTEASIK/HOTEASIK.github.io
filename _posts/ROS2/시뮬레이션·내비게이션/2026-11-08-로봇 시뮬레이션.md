# 로봇 시뮬레이션

## 정의·핵심
- **정의**: 중력·충돌·마찰이 있는 가상 세계에서 로봇을 실제처럼 굴려 보는 일 — 「위험한 첫 시도」를 안전하게 받아 주는 완충 지대 (기초 5.5, 실습 5차시).
- **로봇 개발의 딜레마**: 진짜 로봇은 비싸고, 떨어뜨리면 부서지고, 실험실에 한 대뿐 → 코드를 검증하려면 움직여 봐야 하는데, 검증 안 된 코드는 벽·사람 쪽으로 돌진할 수 있다 → 가상에서는 코드가 엉망이어도 부서지는 것도 다치는 사람도 없다.
- **RViz는 모니터, Gazebo는 무대**: RViz는 토픽을 받아 「로봇이 아는 것」을 그릴 뿐 계산·생성하지 않는다. Gazebo는 「실제로 일어나는 것」을 계산하고 가상 센서값을 만들어 토픽으로 낸다.
- **창의 문제인가, 세계의 문제인가**: RViz에서 로봇이 안 보이면 표시 설정을, Gazebo에서 안 움직이면 명령이 안 닿았거나 끼인 것을 의심. 두 창을 나란히 — Gazebo에선 벽 앞인데 RViz 지도에 벽이 없으면 「인식이 늦거나 끊겼다」.
- **비용 절감 그 이상**: 센서 고장·갑작스러운 장애물·미끄러운 바닥을 설정 하나로 만들고, 같은 초기 조건으로 고친 알고리즘을 공정하게 견준다(재현성).
- **현실 격차(sim-to-real gap)**: 가상 물리는 근사 — 마찰·미끄러짐·센서 잡음 차이가 실로봇에서 다르게 나타난다. 큰 결함은 시뮬레이션에서 걸러 내고 마지막엔 반드시 실로봇으로.
- **물리가 있어야 답하는 물음**: 경사로에서 미끄러지나, 문턱을 넘나, 빨리 돌면 넘어지나 → URDF에 collision·inertial이 필요한 까닭.
- **디지털 트윈**: 실제 로봇과 똑같은 가상 쌍둥이(대표 도구 NVIDIA Isaac Sim)로 먼저 다 테스트하고 현실에 옮긴다 — ABB·FANUC·KUKA가 생산 라인을, 나아가 로봇 군집(fleet)을 통째로 미리 돌린다.
- **이 과정의 흐름**: Gazebo(무대) → ros_gz 다리 → slam_toolbox(지도를 그리는 손) → Nav2(운전사), 그리고 같은 ROS2 위의 팔(두산).

## 원리·구조
| 구분 | RViz | Gazebo |
|---|---|---|
| 하는 일 | 데이터 시각화 | 물리 시뮬레이션 |
| 물리 계산 | 안 함 | 함 |
| 데이터 방향 | 토픽을 받아 그림 | 가상 센서를 만들어 내보냄 |
| 한마디 | 로봇이 아는 것 | 실제로 일어나는 것 |

## 코드 예시
```python
# 증상 → 어느 쪽 문제인가 (창 vs 세계)
def which(rviz_shows_robot, robot_moves_in_gazebo, wall_in_gazebo, wall_in_rviz_map):
    if not rviz_shows_robot and robot_moves_in_gazebo: return "창(RViz 표시 설정·Fixed Frame)"
    if not robot_moves_in_gazebo: return "세계(명령이 안 닿음·끼임)"
    if wall_in_gazebo and not wall_in_rviz_map: return "인식이 늦거나 끊김(센서·SLAM)"
    return "정상"
print(which(False, True, True, True))   # 창(RViz 표시 설정·Fixed Frame)
print(which(True, False, True, True))   # 세계(명령이 안 닿음·끼임)
print(which(True, True, True, False))   # 인식이 늦거나 끊김(센서·SLAM)
```
