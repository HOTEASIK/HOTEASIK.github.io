## 0. 시험 직전 1분 요약

| 외울 것 | 답 |
|---|---|
| 계층 | User code → rcl(rclpy/rclcpp) → **rmw** → DDS (`ros_core` 없음) |
| 노드 일생 | `init → spin → shutdown` |
| 구분선 `---` 개수 | msg 0 / srv 1 / action 2 |
| `.action` 칸 순서 | **Goal → Result → Feedback** (시간 순서 아님) |
| 액션 횟수 | 목표 1, 피드백 0~N, 결과 1, 취소 0~1 |
| 종결 도장 | `succeed()` / `abort()` / `canceled()` — 없으면 ABORTED |
| 막힘 해결 2조건 | `MultiThreadedExecutor` **+** 서로 다른 콜백그룹 |
| 타이머 주기 → Hz | `create_timer(0.2, …)` = 5Hz, `0.1` = 10Hz |
| entry point | `실행이름 = 패키지.모듈:함수` |
| launch 등록 | `setup.py`의 `data_files`에 `glob('launch/*.launch.py')` |
| source 규칙 | 빌드는 한 번, source는 매번 / underlay 먼저, overlay 나중 |
| colcon build 위치 | 워크스페이스 최상위 (`src` 안 ❌) |
| 로그 등급 | DEBUG < INFO < WARN < ERROR < FATAL (기본 INFO 이상) |
| QoS 비호환 | 발행 BEST_EFFORT + 구독 RELIABLE → **아무것도 안 옴** |
| 이름 가르기 | DOMAIN_ID(네트워크) / remap(토픽 하나) / namespace(노드 전체) |
| bag 형식 | Jazzy 기본 **mcap**, 직렬화 **CDR** |
| 진단 사다리 | node list → topic list/info → echo → hz → service/action → param |

## 1. 기초 (컴퓨터·네트워크·센서)

| 개념             | 핵심                                                                                                               |
| -------------- | ---------------------------------------------------------------------------------------------------------------- |
| 라이브러리 vs 프레임워크 | 라이브러리는 **내가 부르고**, 프레임워크는 **프레임워크가 내 코드를 부름**. socket은 라이브러리, **ROS는 프레임워크** (→ 콜백을 등록만 하고 spin이 불러 줌)           |
| 프로세스 vs 스레드    | 프로세스끼리는 메모리 격리. 스레드는 메모리를 공유해서 **동기화(lock)** 필요 → 10장 Reentrant 경쟁 상태와 연결                                        |
| 컴파일러 vs 인터프리터  | C++은 컴파일 언어라 빠름(실시간 제어). Python은 인터프리터라 개발이 빠름                                                                   |
| IP / 포트 / 소켓   | IP는 컴퓨터, 포트는 그 안의 프로그램, 소켓은 둘을 묶은 통신 창구                                                                          |
| TCP vs UDP     | TCP는 신뢰성(재전송), UDP는 빠르지만 유실 가능. 영상은 UDP, 명령은 TCP → QoS RELIABLE/BEST_EFFORT와 같은 발상                               |
| 소켓 순서          | 서버: `socket → bind → listen → accept`, 클라이언트: `connect`. accept/recv에서 멈추는 건 **블로킹**. 상대가 끊으면 `recv()`가 빈 바이트 반환 |
| OSI 7 Layer    | 층을 나누면 한 층이 바뀌어도 다른 층은 영향 없음. 장애 위치를 층별로 좁혀 찾음                                                                   |
| UART           | TX와 RX는 X자 교차. 양쪽이 **보드레이트·데이터비트·패리티·스톱비트**를 맞춤                                                                  |
| 센서 흐름          | 아날로그 → **ADC**(샘플링·양자화·부호화) → 처리 → **DAC/PWM** → 구동                                                              |
| 로봇             | 인지 → 판단 → 행동. 구성은 센서·제어기·구동기                                                                                     |
| 센서 퓨전          | 라이다는 정확한 거리, 카메라는 의미 정보. 서로 보완                                                                                   |
| REP-103        | `base_link`: **X 앞, Y 왼쪽, Z 위**. **카메라 광학 프레임**: **Z 앞, X 오른쪽, Y 아래**                                            |
| 쿼터니언           | 오일러각의 **짐벌락**(축이 겹쳐 자유도를 잃음)이 없고, 보간이 매끄럽고 안정적                                                                   |
| 미들웨어           | OS 위의 통신 계층(ROS). 펌웨어는 하드웨어 안의 저수준 SW                                                                            |

## 2. ROS2 구조와 노드 뼈대

### 개념

- **원칙: "통신은 ROS, 로직은 나"** — IP·포트·재연결·직렬화는 ROS가 맡고, 개발자는 **이름과 타입만 맞춤**
- **ROS1과 다른 점**: Master 없음, DDS로 **자동 발견**, 멀티 OS 지원
- **계층**: User code → rcl(rclpy/rclcpp) → **rmw** → DDS — 객관식 함정: `ros_core`는 없음
- **rclpy 구성요소**: 노드, 퍼블리셔, 서비스/클라이언트, 액션 (라우터는 없음)
- **rclpy 4요소**: 초기화 → 노드 정의 → 통로 열기(pub/sub/timer) → 살려두기(spin)
- **패키지 이름**: 소문자로 시작, 소문자·숫자·`_`만. `-`(빼기 연산자로 읽힘), `2dlidar`, `MyRobot` ❌
- **한 노드 한 책임**: 노드 설명에 "그리고"가 들어가면 나눔
- **`source /opt/ros/jazzy/setup.bash`** 빠뜨리면 `ros2: command not found`

### 수업 코드의 공통 뼈대 (모든 노드가 이 모양) — [코드 #40 my_publisher.py]

```python
import rclpy
from rclpy.node import Node
from rclpy.executors import ExternalShutdownException

class MyPublisher(Node):
    def __init__(self):
        super().__init__('my_publisher')      # ② 노드 정의 (노드 이름)
        ...                                    # ③ 통로 열기 (pub/sub/timer/service/action)

def main():
    rclpy.init()                               # ① 초기화
    node = MyPublisher()
    try:
        rclpy.spin(node)                       # ④ 살려두기 — 대부분의 시간을 여기서
    except (KeyboardInterrupt, ExternalShutdownException):
        pass
    finally:
        node.destroy_node()
        rclpy.try_shutdown()                   # 이미 꺼졌어도 에러 없이 종료

if __name__ == "__main__":
    main()
```

> ⚠ **노드 이름 중복**: [코드 #38] `rocket_pub.py`의 클래스는 `RoketPublisher`지만 노드 이름은 `'my_publisher'`입니다. `my_publisher`와 함께 띄우면 같은 이름 노드가 두 개 → `ros2 node list`에 경고, 파라미터·서비스 대상이 헷갈립니다.

**선택 질문**: 계속 흐르나? → 토픽 / 한 번 묻고 답하나? → 서비스 / 오래 걸리고 진행·취소가 필요하나? → 액션 / 설정인가? → 파라미터

**설계 절차 4단계**: 기능 나열 → 데이터 성질 파악 → 통신 선택 → 노드·인터페이스 배치

**잘못 고르면**

| 잘못된 선택 | 결과 |
|---|---|
| 순찰을 서비스로 | 진행 상황 X, 취소 X, 클라이언트가 묶임 |
| 상태를 서비스로 | 누가 물어야만 알 수 있음 |
| 명령을 토픽으로 | 받았는지 확인할 응답이 없음 |
| 긴 작업을 서비스로 | 클라이언트가 막히고 타임아웃 |
| 한 번이면 될 설정을 토픽으로 | 같은 값 반복 전송, 자원 낭비 |

## 4. 토픽 — 퍼블리셔/구독

### 개념

| | 타이머 | 구독 |
|---|---|---|
| 계기 | 일정 시간마다 | 메시지 도착 시 |
| 등록 함수 | `create_timer(주기, 콜백)` | `create_subscription(타입, 이름, 콜백, QoS)` |
| 콜백 인자 | 없음 | `msg` |

- `create_timer(0.2, ...)` = 5Hz. `while`로 계속 살피면 자원 낭비
- **느슨한 결합**: 발행자·구독자는 이름과 타입만 공유 → 구독자가 늘어도 발행자 코드는 그대로
- **QoS depth** = 큐 크기. 작으면 유실, 크면 지연·메모리 증가

### 코드 — [코드 #40 my_publisher] + [코드 #36 my_subscriber]

```python
# 발행
self.pub = self.create_publisher(String, 'chatter', 10)   # 타입, 이름, depth
self.create_timer(1.0, self.tick)                          # 1Hz
def tick(self):
    msg = String()
    msg.data = f"Hello ROS : {self.num}"
    self.pub.publish(msg)

# 구독
self.create_subscription(String, 'chatter', self.cb, 10)
def cb(self, msg):
    self.get_logger().info("수신함 : " + msg.data)
```

## 5. 서비스 — 서버/클라이언트

### 개념

- **서비스 = 원격 함수 호출(RPC)**: 요청=인자, 서버 콜백=함수, 응답=반환값
- **서버 콜백 시그니처는 `(self, request, response)`**, 반드시 `return response`
- **`call_async` → `future`**: 나중에 결과가 채워질 약속 객체
  - **콜백 안에서 동기로 기다리면 데드락** (응답을 처리할 실행 흐름을 자기가 붙잡고 있음)
- **개발 순서**: 서버 → `ros2 service call`로 검증 → 클라이언트
- **칸 이름 오류는 바로 에러, 자료형 오류는 조용히 지나갈 수 있어서 더 위험**

### 서버 — [코드 #37 add_server]

```python
self.create_service(AddTwoInts, 'add_two_ints', self.on_request)

def on_request(self, req, res):
    res.sum = req.a + req.b
    return res
```

### 클라이언트 — [코드 #35 add_client]

```python
self.cli = self.create_client(AddTwoInts, 'add_two_ints')
while not self.cli.wait_for_service(timeout_sec=1.0):     # 서버가 뜰 때까지 재시도
    self.get_logger().info("서버 접속 시도 중.....")

def send(self, a, b):
    req = AddTwoInts.Request(); req.a = a; req.b = b
    future = self.cli.call_async(req)
    rclpy.spin_until_future_complete(self, future)          # main에서 부르므로 OK
    return future.result()
```

> ✅ 여기서는 `send()`를 **main에서** 부르므로 `spin_until_future_complete`가 안전합니다.
> ❌ 같은 코드를 **타이머·구독 콜백 안에서** 부르면 데드락 → 콜백 안에서는 `future.add_done_callback(...)`을 써야 합니다.

CLI 검증:
```bash
ros2 service call /add_two_ints example_interfaces/srv/AddTwoInts "{a: 1, b: 2}"
```

### 실패를 응답으로 표현 — [코드 #27 calc_server] (Calc.srv: `a, b, op` → `result, ok`)

```python
if op == "+":   response.result = a + b; response.ok = True
elif op == "/": response.result = a / b; response.ok = True   # ⚠ b=0이면?
else:           response.ok = False
```

> ⚠ **함정**: `Calc.srv`에 `bool ok`를 둔 이유는 **0으로 나누기 같은 실패를 결과값과 구분**하려는 것인데, 이 코드는 `b == 0`을 검사하지 않아 `ZeroDivisionError`로 콜백이 터집니다. `if b == 0: response.ok = False`가 먼저 와야 합니다.

## 6. 액션 — 서버/클라이언트

### 개념

- **액션 = 서비스 + 토픽**: 목표·결과는 서비스 방식(`send_goal_async`, `get_result_async`), 피드백은 토픽 방식(`publish_feedback`)
- **횟수**: 목표 1, 피드백 0~N, 결과 1, 취소 0~1
- **구성요소**: Goal, Result, Feedback, Client (Timeout은 아님)
- **`goal_handle`로 하는 일**: `request`(목표 읽기), `publish_feedback`, `is_cancel_requested`
- **종결 도장**: `succeed()` / `abort()` / `canceled()` — 없으면 경고 + **ABORTED**, `return` 결과가 없으면 클라이언트 무한 대기
- 행맨에서 진 판 = `SUCCEEDED` + `won: false` (abort는 작업 자체를 못 했을 때만)
- **취소 5단계**: `cancel_goal_async` → `cancel_callback`이 ACCEPT → 실행 루프에서 `is_cancel_requested` 확인 → `canceled()` → Result 반환
  - `is_cancel_requested`를 안 보면 3단계에서 끊김 / 단일 스레드면 2단계에서 끊김

### 서버 — [코드 #30 count_up_server]

```python
ActionServer(self, CountUp, "count_up", self.execute)

def execute(self, goal_handle):                 # 인자는 goal_handle 하나
    target = goal_handle.request.target          # ① 목표 읽기
    seq, fb = [], CountUp.Feedback()
    for i in range(1, target + 1):
        seq.append(i)
        fb.current = i
        goal_handle.publish_feedback(fb)         # ② 피드백 0~N번
        time.sleep(1)
    goal_handle.succeed()                        # ③ 종결 도장
    result = CountUp.Result()
    result.sequence = seq
    return result                                # ④ 결과 반환
```

> 콜백 시그니처 비교 (코드 주석에 있던 내용): 액션 `(self, goal_handle)` / 서비스 `(self, req, res)` / 구독 `(self, msg)` / 타이머 `(self)`

> ⚠ 이 서버는 **취소를 지원하지 않습니다**: `cancel_callback` 등록도, 루프 안 `is_cancel_requested` 확인도 없고, 단일 스레드 `rclpy.spin`입니다 (취소 5단계 중 2·3단계 모두 없음).

### 클라이언트 — [코드 #29 count_up_client] 콜백 사슬

```python
self.cli = ActionClient(self, CountUp, "count_up")

def send(self, target):
    goal = CountUp.Goal(); goal.target = target
    self.cli.wait_for_server()
    fut = self.cli.send_goal_async(goal, feedback_callback=self.on_fb)   # 피드백 콜백 등록
    fut.add_done_callback(self.on_accept)                                # ① 수락 여부

def on_accept(self, fut):
    gh = fut.result()                       # goal handle
    if gh.accepted:
        gh.get_result_async().add_done_callback(self.on_result)          # ② 결과 대기

def on_result(self, fut):
    self.get_logger().warn(f"작업 완료 : {fut.result().result.sequence}")
    rclpy.shutdown()                        # 결과 받으면 spin 종료

def on_fb(self, msg):
    self.get_logger().info(f"현재 피드백 : {msg.feedback.current}")    # msg.feedback.필드
```

**흐름**: `send_goal_async` → (수락) `on_accept` → `get_result_async` → `on_result`, 그 사이 `on_fb` 0~N번

CLI 검증:
```bash
ros2 action send_goal /count_up my_interfaces/action/CountUp "{target: 3}" --feedback
```

## 7. 파라미터

### 개념

- **선언**: `self.declare_parameter('speed', 1.0)` — 기본값이 **값과 타입**을 함께 정함
- **읽기**: `self.get_parameter('speed').value`
- **`__init__`에서 한 번만 읽으면 `param set`이 반영 안 됨** → 쓰는 시점(콜백 안)에서 읽기
- **설정 콜백 `add_on_set_parameters_callback`**: 바뀌기 **전에** 검증. 거부하면 애초에 안 바뀜 (바꿨다가 되돌리는 게 아님)

| 값을 주는 길 | 시점 |
|---|---|
| `-p name:=value` | 시작할 때, 하나씩 |
| `--params-file x.yaml` | 시작할 때, 여러 개 |
| launch `parameters=[{...}]` | 시작할 때 |
| `ros2 param set` | 실행 중 |

- `param dump`는 현재 값 저장, `param load`는 실행 중인 노드에 적용
- **타이머 주기는 만들 때 고정** → 바꾸려면 설정 콜백에서 `destroy_timer` 후 재생성
- **YAML 노드 이름 오타는 에러 없이 무시**되고 코드 기본값으로 돔

## 8. 인터페이스 (.msg/.srv/.action)

- **구분선 `---`**: msg 0개 / srv 1개 / action 2개
- **`.action` 칸 순서 Goal → Result → Feedback** ⚠ 시간 순서로 뒤집는 실수 많음
- **타입 읽기**: `std_msgs/msg/String` = 패키지 / 종류 / 이름 — `std_msgs`(기본형), `geometry_msgs`(Twist·Pose), `sensor_msgs`(Image·LaserScan·Imu)
- **인터페이스가 정하는 것**: 칸 **이름**과 **타입** (값이 아니라 모양). `"leo,5.0,2.0"`처럼 이어 붙이면 순서 착오가 에러 없이 지나감

| 표기 | 예 | 규칙 |
|---|---|---|
| 필드 | `float64 speed` | 소문자 |
| 기본값 | `float64 speed 1.0` | 단순 타입만 |
| 상수 | `int8 PLUS=1` | 대문자 + `=` |

## 10. Executor·콜백그룹 ⭐

### 개념

- **spin 한 바퀴**: 수집 → 선택 → 실행 → 반복 (주간 퀴즈 답: "대기 → 선택 → 실행")
  - 막히는 지점은 **실행** 단계. 놓친 타이머 차례는 **사라짐** (몰아서 처리 안 함)
- **기본값이 단일 스레드인 이유**: 콜백끼리 충돌 없고 예측 쉬움
- **막힘을 풀려면 두 조건 모두**: ① `MultiThreadedExecutor` ② 콜백을 **서로 다른 그룹**에
- **콜백그룹**
  - `MutuallyExclusive`: 그룹 안에서 한 번에 하나. 권장 기본값 (아무것도 안 주면 노드의 기본 그룹 하나 = MutuallyExclusive)
  - `Reentrant`: 같은 그룹 콜백도 겹쳐 돔 → **경쟁 상태** 위험
- **액션 서버 막힘은 실행기(MultiThreaded)가 풂** — 실행 함수는 별도 task라 그룹 설정과 무관
- **타이머 주기가 짧을수록 CPU 부하 증가** (객관식 함정)

### 코드 — [코드 #31 executor_demo] 네 조합 실험

```python
USE_MULTI = True
SPLIT_GROUP = True

self.create_timer(0.5, self.fast_cb)                         # 기본 그룹
if SPLIT_GROUP:
    self.create_timer(2.0, self.slow_cb, callback_group=MutuallyExclusiveCallbackGroup())
else:
    self.create_timer(2.0, self.slow_cb)                     # 같은 기본 그룹

def slow_cb(self):
    time.sleep(5)                                            # 5초 막힘

# main
if USE_MULTI:
    ex = MultiThreadedExecutor(); ex.add_node(node); ex.spin()
else:
    rclpy.spin(node)
```

| USE_MULTI (여러개 인가?) | SPLIT_GROUP (그룹을 나누나) | slow_cb가 자는 5초 동안 fast_cb는? | 이유                              |
| ------------------- | --------------------- | --------------------------- | ------------------------------- |
| False               | False                 | ❌ 멈춤                        | 일손 1개                           |
| False               | True                  | ❌ 멈춤                        | 그룹은 나눴지만 일손 1개                  |
| True                | False                 | ❌ 멈춤                        | 일손은 많지만 같은 MutuallyExclusive 그룹 |
| **True**            | **True**              | ✅ 계속 돎                      | 두 조건 충족                         |

### 수업 코드의 그룹 배치 패턴

| 코드 | 실행기 | 그룹 배치 | 목적 |
|---|---|---|---|
| [#25] calculator | Multi | 구독=기본, 서비스=`group1`(Reentrant), 액션=`group2`(Reentrant) | 액션이 도는 동안에도 숫자 수신·연산 서비스 가능 |
| [#20] game_node_action | Multi | 액션+서비스 모두 같은 `Reentrant` 그룹 | 액션 루프가 자는 동안 `guess_letter` 서비스 처리 |
| [#12] robot_patrol | Multi | 액션+구독+서비스 모두 같은 `Reentrant` 그룹 | 순찰(sleep) 중에도 온도 갱신·보고서 응답 |

> ⚠ Reentrant 하나에 다 넣으면 막힘은 풀리지만 `self.found`, `self.issue_count` 같은 공유 상태를 여러 스레드가 동시에 건드립니다 → **경쟁 상태** 가능 (교재 권장: 그룹을 나누고 MutuallyExclusive 기본).

## 12. QoS

| 정책 | 값 | 뜻 |
|---|---|---|
| Reliability | `RELIABLE` / `BEST_EFFORT` | 재전송 보장 / 빠르지만 유실 가능 |
| Durability | `VOLATILE` / `TRANSIENT_LOCAL` | 지난 메시지 없음 / **늦게 온 구독자에게 마지막 메시지 전달** |
| History | `KEEP_LAST`(+depth) / `KEEP_ALL` | 최근 N개 / 전부 |

### 호환 규칙 (요청 ≤ 제공이어야 연결)

| 발행자 | 구독자 | 결과 |
|---|---|---|
| RELIABLE | RELIABLE | ✅ |
| RELIABLE | BEST_EFFORT | ✅ |
| **BEST_EFFORT** | **RELIABLE** | ❌ **아무것도 안 옴** (에러 없이 조용히) |
| TRANSIENT_LOCAL | VOLATILE | ✅ |
| **VOLATILE** | **TRANSIENT_LOCAL** | ❌ |

### 코드 — [코드 #7 qos_talker] / [코드 #6 qos_listener]

```python
from rclpy.qos import QoSProfile, ReliabilityPolicy, HistoryPolicy, DurabilityPolicy

qos = QoSProfile(reliability=ReliabilityPolicy.BEST_EFFORT,
                 history=HistoryPolicy.KEEP_LAST, depth=10)
self.pub = self.create_publisher(String, 'qos_chat', qos)
self.create_subscription(String, "qos_chat", self.on_msg, qos_profile=qos)
```
> listener 주석의 `RELIABLE` 줄로 바꾸면 talker(BEST_EFFORT)와 **비호환 → 수신 0건**. 이것이 실습의 핵심.

### CLI 실습 — [코드 #8]

```bash
ros2 topic pub /chatter std_msgs/msg/String "{data: hi}" --qos-reliability best_effort
ros2 topic echo /chatter --qos-reliability reliable     # → 아무것도 안 옴
ros2 topic info /chatter --verbose                       # → 양쪽 QoS 확인 (진단용)
```

### 늦게 온 구독자에게 지도 전달 — [코드 #4 map_pub]

```python
map_qos = QoSProfile(reliability=ReliabilityPolicy.RELIABLE,
                     durability=DurabilityPolicy.TRANSIENT_LOCAL, depth=10)
self.pub = self.create_publisher(String, "map_info", map_qos)
self.timer = self.create_timer(1, self.pub_map_info)

def pub_map_info(self):
    ...
    self.pub.publish(msg)
    self.timer.cancel()           # 한 번만 발행
```
> 한 번만 발행해도 `TRANSIENT_LOCAL`이라 **나중에 접속한 구독자도 받음** (구독자도 TRANSIENT_LOCAL이어야 함).
> 9장 "한 번 쏘고 끝나는 발행은 유실" 문제의 대처법 중 하나(`sleep`, `topic pub -w`, `transient_local`)가 바로 이것.

```bash
ros2 topic echo /map_info --qos-durability transient_local --qos-reliability reliable
```

### 코드로 쓰기 — [코드 #16 bag_writer] : 어디에 · 어떻게 · 무엇을 · 언제

```python
import rosbag2_py
from rclpy.serialization import serialize_message

writer = rosbag2_py.SequentialWriter()
writer.open(
    rosbag2_py.StorageOptions(uri='code_bag', storage_id='mcap'),                    # 어디에
    rosbag2_py.ConverterOptions(input_serialization_format='cdr',
                                output_serialization_format='cdr'))                  # 어떻게
writer.create_topic(rosbag2_py.TopicMetadata(id=0, name='/chatter',
                    type='std_msgs/msg/String', serialization_format='cdr'))         # 무엇을
for i in range(10):
    msg = String(); msg.data = f'hi from code {i}'
    writer.write('/chatter', serialize_message(msg), i * 1_000_000_000)              # 언제(ns)
del writer
```

### 코드로 읽기 — [코드 #15 bag_read]

```python
reader = rosbag2_py.SequentialReader()
```

## 15. 종합 예제: 계산기 · 행맨 · 순찰 로봇

### 15-1. 계산기 — [코드 #26 argument] + [코드 #25 calculator]

**통신 배치**: 두 수는 **토픽**, 연산자는 **서비스**, 누적 점검은 **액션**, 범위는 **파라미터**

```
argument ──(topic: arithmetic_argument)──▶ calculator
   ▲ param: min/max_random_num               ├─ service: arithmetic_operator  ◀── ros2 service call
                                             └─ action:  arithmetic_checker   ◀── ros2 action send_goal
```

```bash
ros2 service call /arithmetic_operator my_interfaces/srv/ArithmeticOperator "{arithmetic_operator: 1}"
ros2 action send_goal /arithmetic_checker my_interfaces/action/ArithmeticChecker "{goal_sum: 100.0}" --feedback
ros2 param set /argument max_random_num 19
```

**액션 로직**: 마지막 연산 결과를 `goal_sum`을 넘기 직전까지 누적하며 피드백

```python
while True:
    total += argument_result
    if total > goal_sum:
        total -= argument_result     # 넘으면 한 번 되돌리고 종료
        break
    feedback.current_num = total
    goal_handle.publish_feedback(feedback)
    time.sleep(1)
```

**코드에서 볼 함정**
1. `on_operator`는 `PLUS`만 처리 → 다른 연산자를 보내면 `result`가 정의되지 않아 `UnboundLocalError`
2. `argument_result`가 0 이하(연산 서비스를 한 번도 안 부른 경우 0.0)면 `total`이 커지지 않아 **액션이 끝나지 않음**
3. 실행기·그룹: 구독은 기본 그룹, 서비스·액션은 각각 다른 Reentrant 그룹 + MultiThreaded → 액션 도중에도 서비스·구독 처리 가능

**노드를 나누는 기준**: 결합도·재사용 / 디버깅·교체 / 구성 복잡도·통신 비용

### 15-2. 행맨 (토픽 버전) — [코드 #21 game_node] + [코드 #17 game_client]

```
game_client ──(guess: String, 1초마다 a,b,c…)──▶ game_node ──(board: "r _ _ _ _")──▶ 누구나 구독
```

```python
def on_guess(self, msg):
    letter = msg.data.strip().lower()
    if len(letter) != 1:
        self.get_logger().info("한 글자만 들어와야 합니다")   # ⚠ return이 없음!
    if letter in self.answer:
        self.found.add(letter)
    board_msg.data, done = self.check_board()
    self.pub.publish(board_msg)

def check_board(self):
    done = all(ch in self.found for ch in self.answer)
    return " ".join(ch if ch in self.found else "_" for ch in self.answer), done
```

**함정**
- `if letter in answer`: 부분 문자열 `"ro"`, 빈 문자열 `""`도 True → **길이 검증 후 반드시 return**
- 이 코드는 길이 검증 뒤 `return`이 없어서 `"ro"`가 그대로 정답 처리됨
- `game_client`의 `alphabets.pop(0)`은 리스트가 비면 `IndexError` (게임 끝난 뒤 계속 돔). 리스트에 `v, w, x, z`도 빠져 있음
- **보드를 토픽으로 만든 이유**: 여러 쪽이 봐야 해서 (서비스 응답은 요청자 한 명에게만)
- **상태 위치는 수명으로**: 여러 콜백에 걸치면 `self.found`, 한 판 동안만이면 지역 변수

### 15-3. 행맨 (액션+서비스 버전) — [코드 #20 game_node_action]

```
클라이언트 ─(action play_round: word)─▶ execute_callback: done될 때까지 1초마다 변화 감지 → feedback
클라이언트 ─(service guess_letter: letter)─▶ on_guess: found 갱신, board·correct·done 응답
```

- 같은 Reentrant 그룹 + MultiThreaded → 액션 루프가 `sleep`하는 동안 서비스가 `self.done`을 바꿔 루프 종료
- **함정**: `self.found`, `self.done`이 판이 끝나도 초기화되지 않음 → 두 번째 판은 시작하자마자 끝남 (상태 수명 문제)
- 오답 분기에서 `res.done`을 안 채움 (기본값 False라 동작은 하지만 일관성 없음)
- 길이 검증 분기는 `return res`가 있어서 토픽 버전보다 안전

### 15-4. 순찰 로봇 — [코드 #9, #10, #12]

```
robot_sensor ──(topic robot/temperature: Float64)──▶ robot_patrol
  param: threshold, base_temp                         ├─ action  robot/patrol (zone → 방마다 feedback)
                                                      ├─ service robot/report (Trigger: 순찰/이슈 횟수)
                                                      └─ param   limit (화재 판정 온도, 기본 50.0)
```

```python
self.zone = {"a": [1, 1, 2, 2], "b": [2, 1, 2, 1, 2]}     # 방마다 순찰 시간(초) = 중요도

for room_num, room_importance in enumerate(patrol_map):
```

### C. 코드 분석

- **C1.** `b == 0`이면 `ZeroDivisionError`로 콜백이 터지고 응답이 안 감. 또 `"/"` 외의 연산자는 `ok`를 안 채움.
  ```python
  if request.op == "/" and request.b == 0:
      response.ok = False
      return response
  ```
- **C2.** `{"r", "ok", ""}` — 길이 검증 후 `return`이 없고, `"ok" in "rokey"`와 `"" in "rokey"`가 모두 True. 검증 분기에 `return` 추가.
- **C3.** `__init__`에서 한 번만 읽어 `self.speed`에 저장했기 때문. `tick` 안에서 `self.get_parameter("speed").value`로 매번 읽기.
- **C4.** 실행되지 않음. 두 타이머가 모두 노드의 기본 그룹(MutuallyExclusive) 하나에 있어서, 일손이 여러 개여도 같은 그룹 콜백은 한 번에 하나만 돎.
- **C5.** 데드락. 콜백이 실행 흐름을 붙잡고 있어서 응답을 처리할 spin이 돌지 못함. 대안: `future.add_done_callback(self.on_response)`로 비동기 처리 (또는 MultiThreaded + 다른 그룹).
- **C6.** `LaunchDescription(` 의 닫는 `)`가 없음 → SyntaxError. `]` 뒤에 `)` 추가.
- **C7.** `if`에서 PLUS만 처리하므로 `result`가 할당되지 않은 채 `res.arithmetic_result = result` 실행 → `UnboundLocalError`, 서비스 응답 실패. `elif`로 나머지 연산자와 `else` 처리 필요.
- **C8.** `send_goal_async` / `accepted` / `get_result_async`

### D. 서술형 (모범 답안 요지)

- **D1.** ① 진행 상황(피드백)을 볼 수 없음 ② 중간에 취소할 수 없음 ③ 응답이 올 때까지 클라이언트가 묶이고 타임아웃 위험. 액션은 목표 → 피드백 0~N → 결과 구조로 진행을 보고하고, `cancel_goal_async`로 취소할 수 있어 오래 걸리는 작업에 적합.
- **D2.** `ros2 node list`로 두 노드 존재 확인 → `ros2 topic list`에서 비슷한 이름 토픽 두 개 발견 → `ros2 topic info`로 각 토픽의 발행자 1·구독자 0 / 발행자 0·구독자 1 확인 → 이름 수정 또는 remap(`-r 틀린이름:=맞는이름`) → `topic echo`·`topic hz`로 실제 값과 주기 확인. "오류가 없다고 정상은 아니다", 존재부터 내용으로 좁혀 감.
- **D3.** 순찰 액션이 방마다 `time.sleep()`으로 실행 흐름을 오래 잡고 있으므로, 그 동안 온도 구독이 `current_temp`를 갱신하고 보고서 서비스가 응답하려면 여러 스레드(MultiThreaded)와 동시 실행 가능한 그룹(Reentrant)이 필요. 위험: 여러 콜백이 `self.current_temp`, `self.issue_count`, `self.patrol_count`를 동시에 읽고 써서 경쟁 상태가 생길 수 있음. 또 없는 zone이면 `KeyError`.
- **D4.** ① 클라이언트 `cancel_goal_async` ② 서버 `cancel_callback`이 ACCEPT ③ 실행 루프에서 `is_cancel_requested` 확인 ④ `goal_handle.canceled()` ⑤ Result 반환. count_up_server는 `cancel_callback`을 등록하지 않았고(기본은 거절), 루프에서 `is_cancel_requested`를 확인하지 않으며, 단일 스레드 `rclpy.spin`이라 실행 중에는 취소 요청을 처리할 일손도 없음.
- **D5.** 보드 상태는 플레이어·관전자·로거 등 **여러 쪽이 봐야** 하는 데이터. 서비스 응답은 요청한 클라이언트 한 명에게만 가지만, 토픽은 구독자 수에 상관없이 모두에게 전달되고 발행자 코드는 바뀌지 않음(느슨한 결합).
