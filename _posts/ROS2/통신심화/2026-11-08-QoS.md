# QoS

## 정의·핵심
- **정의**: QoS(Quality of Service, 통신 품질) — 보내는 쪽과 받는 쪽이 **통신을 시작하기 전에 맺는 약속**. 「데이터를 어떤 방식으로 주고받을지 미리 정해 둔 규약」 (실습 2차시).
- **통신은 양쪽의 합의로 성립한다**: 약속이 어긋나면 ROS는 두 노드를 **아예 잇지 않는다** — 데이터가 사라진 게 아니라 길이 연결되지 않았다. 프로그램은 멈추지 않고 양쪽 터미널에 경고 한 줄만 남는다.
- **왜 따로 정하나**: 데이터가 한 종류가 아니다 — 라이다(초당 수십 번, 몇 개 빠져도 됨), 지도(한 번 받으면 끝), 「정지!」 명령(한 번만 놓쳐도 사고). 모두 같은 약속이면 센서에는 과하고 명령에는 부족하다.
- **바탕은 DDS 표준**: DDS가 제공하는 항목은 스물이 넘지만 실무에서 자주 쓰는 건 넷 — [[QoS Reliability]] · [[QoS Durability]] · [[QoS History와 Depth]](이력·깊이는 한 쌍). 나머지(데드라인·활성 상태 감시·수명)는 대부분 기본값.
- **입문 때 숫자 10 하나로 통한 까닭**: `create_publisher(String, 'chatter', 10)`은 depth만 10, 나머지는 기본값(보통 RELIABLE·VOLATILE) — 양쪽이 같은 기본값이었기 때문. 한쪽만 바꾸는 순간 어긋난다.
- **만들 때 정해진다**: 퍼블리셔·서브스크라이버를 생성하는 순간 굳는다 — 실행 중에 돌리는 손잡이가 아니다. 바꾸려면 코드를 고쳐 다시 띄운다.
- **「있다」와 「맞는다」는 다르다**: 양쪽 다 분명히 설정해도 서로 맞물리지 않을 수 있다 → [[QoS 호환 규칙]].
- **현장**: QoS 불일치는 「가장 오래 헤매는 버그」 부류. WiFi 위에서 RViz가 RELIABLE 무거운 토픽을 끌어가면 재전송이 쌓여 로봇이 멈추기도 한다 — 센서는 BEST_EFFORT.

## 원리·구조
| 항목 | 택배로 그리면 | 질문 |
|---|---|---|
| 신뢰성 reliability | 등기(재발송 보장) / 일반 | 빠짐 방지 |
| 지속성 durability | 경비실이 맡아 두었다 나중에 줄지 | 늦은 수령 |
| 이력·깊이 history·depth | 경비실이 몇 개까지 맡아 둘지 | 보관 개수 |

## 코드 예시
```python
# 새 토픽을 만났을 때 세 질문 → 약속 (실습 2차시 의사결정 흐름)
def choose_qos(must_not_lose, late_joiner_needs_last, is_sensor):
    rel = "RELIABLE" if must_not_lose else "BEST_EFFORT"
    dur = "TRANSIENT_LOCAL" if late_joiner_needs_last else "VOLATILE"
    depth = 5 if is_sensor else 10
    return rel, dur, f"KEEP_LAST({depth})"
print("라이다:", choose_qos(False, False, True))   # 라이다: ('BEST_EFFORT', 'VOLATILE', 'KEEP_LAST(5)')
print("cmd_vel:", choose_qos(True, False, False))  # cmd_vel: ('RELIABLE', 'VOLATILE', 'KEEP_LAST(10)')
print("지도:", choose_qos(True, True, False))      # 지도: ('RELIABLE', 'TRANSIENT_LOCAL', 'KEEP_LAST(10)')
```
