# 배경

중간 점검에서 "공정별 단위 기능만 있고, **전체를 관리하는 매니저와 인터페이스가 없다**"는 지적을 받았습니다.
그래서 공통 Action 양식, DB, 공정 실행기를 만들어 공정을 하나로 묶었습니다.

# 1. 공통 Action — `Process.action` (주요 필드)

```
# Goal
string task_code        # EXPLORE / INNER_EXPLORE / PUTTY_* / SANDING
int32  run_id
int32  gap_id           # 탐색은 -1
float64[3] start_point  # base 기준 mm
float64[3] end_point
float64[12] wall        # 벽 4점 (top, floor, right, left)
---
# Result
bool   success
string error_code       # "" | E_GRIP | E_FORCE | E_SINGULAR | E_TIMEOUT | E_NO_GAP ...
string message
float64[12] wall        # 탐색만
float64[]   gaps        # 탐색만: 틈 1개당 6개
---
# Feedback  (세부 동작 1개가 끝날 때마다 1번 → task_log 1줄)
string  step
bool    step_success
float64[6] joint
float64[6] task
float64[6] force
int32   duration_ms
string  params_json
float64 contact_ratio
string  force_stats_json
```

**왜 Action인가?**

| 방식 | 적합한가 | 이유 |
|---|---|---|
| Topic | X | 결과 보장·취소 없음 |
| Service | X | 수십 초 걸리는 동작 중간 상태를 못 받음 |
| **Action** | O | 피드백(중간 기록) + 결과 + **취소(cancel)** |

# 2. 공정 실행기 — `process_runner.py`

```
run:
  db.start_run
  _steps()        # 시작 단계(0~3)에 따라 탐색을 건너뛸 수 있음
  결과 결정       # 정지 요청 → STOP / ESTOP, 아니면 _steps 결과
  check_run       # 필수 데이터(task_log, wall, gap)가 실제로 남았는지 확인
  db.end_run      # OK / NO_GAP / STOP / ESTOP / E_xxx
```

- 틈이 여러 개일 때
  - 퍼티: 헤라 집기 **1회** → 틈마다 (뜨기 → 도포) → 반납 **1회**
  - 샌딩: 마지막 틈 전까지는 `SANDING_KEEP`(도구를 든 채 다음 틈으로)
- 액션 서버가 **3초 동안 사라져 있으면** 기다리지 않고 실패 처리 (서버가 죽으면 결과가 영영 안 오기 때문)
- 결과 실패도 `<task>_result` step으로 task_log에 남김

# 3. DB 스키마 (테이블 5개)

| 테이블 | 핵심 컬럼 |
|---|---|
| `run` | task, mode, code_version(`git describe`), result, data_check |
| `wall` | run_id, top/floor/right/left 각 xyz |
| `gap` | wall_id, start/end xyz |
| `task_log` | run_id, step, success, error_code, joint·task·force·params(JSON), contact_ratio, duration_ms |
| `quality` | run_id, gap_id, score 1~5, depth_mm |

- `code_version`에 `git describe`를 넣어 **어떤 코드로 돌린 결과인지** 추적
- 연결 오류(`OperationalError`) → `pending.jsonl`에 보관 후 다음 쓰기 성공 시 재전송
- 데이터 오류 → `rejected.jsonl`에 보관, 사람이 확인
- HTTP·공정·피드백 스레드가 연결 하나를 공유 → `threading.Lock` 필수 (없으면 `Packet sequence number wrong`)
- 서버 재시작 시 끝나지 않은 run은 `ABORTED`로 마감

# 4. 웹 HMI — `hmi_server.py`

외부 라이브러리 없이 **표준 라이브러리만** 사용했습니다.

| 클래스 | 역할 |
|---|---|
| `EventHub` | SSE 구독자 관리, 최근 이벤트 400개 보관 |
| `TaskManager` | 시작·정지·비상정지·속도·bringup·그리퍼 |
| `HmiNode` | DSR 서비스 조회(상태, 위치, 힘), joint_states 구독 |

**시작 전 검사**: 모르는 작업 / E-STOP 상태 / 같은 작업 중복 / 로봇 동작 작업 2개 동시 / 액션 서버 모드와 화면 모드 불일치 → 거부

**정지 단계**
- 일반 정지: SIGINT → 8초 뒤 SIGTERM → 15초 뒤 SIGKILL (프로세스 그룹 전체)
- 비상정지: `move_stop(QSTOP)` → 작업 프로세스 SIGKILL(자동 홈 복귀 방지) → 힘·순응 해제 → 속도 잠금. RESET 전까지 새 작업 불가

**속도**: 100% 이하는 컨트롤러 오버라이드로 실행 중 동작에도 즉시 적용

# 5. 설정 — `robot.yaml`

- 소스 폴더의 yaml을 직접 읽어 **빌드 없이 값 변경**
- 공정 goal마다 `config.load()`로 다시 읽음 → 서버 재시작도 필요 없음
- `ROKEY_MODE=virtual`이면 `virtual_override` 섹션 적용 (에뮬레이터 전용 값)

# 6. 로봇 없이 테스트

`fake_db.py`(JSON 파일 DB) + 가짜 Action 서버로 **로봇·MySQL 없이 전체 공정**을 테스트할 수 있게 했습니다.

# 설계와 구현이 달라진 점

| 처음 설계 | 최종 구현 | 이유 |
|---|---|---|
| 웹 → DB `command` 테이블 → 매니저가 0.5초마다 확인 | HMI가 직접 Action 호출 | 경로가 짧고, 상태를 바로 화면에 보여줄 수 있음 |
| 비상정지는 rosbridge WebSocket | HMI HTTP → `move_stop` | rosbridge 의존 제거 |

→ 바뀐 뒤 설계 문서를 갱신하지 못한 것은 아쉬운 점입니다 (06편 회고).
