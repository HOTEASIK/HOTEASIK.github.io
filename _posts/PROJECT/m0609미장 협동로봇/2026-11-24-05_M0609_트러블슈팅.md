# 1. 노드끼리 서로를 못 찾음 — Discovery Server

**증상**
- 같은 launch 안에 가짜 Action 서버가 떠 있는데도 매니저가 3초 안에 `/process/explore`를 못 찾음
- 다른 터미널에서 `ros2 node list`, `ros2 action list` 결과가 비어 있음

**조사**: 실행 중인 프로세스의 환경변수 확인

```bash
tr '\0' '\n' < /proc/<PID>/environ | grep -E "ROS_|RMW"
# ROS_DISCOVERY_SERVER=<이전 프로젝트 서버 IP>:11811   ← 원인
grep -n "ROS_DISCOVERY_SERVER\|ROS_SUPER_CLIENT" ~/.bashrc
```

**원인**: 이전 터틀봇 프로젝트에서 쓰던 **FastDDS Discovery Server** 설정이 `.bashrc`에 남아 있었습니다.
이 설정이 있으면 모든 노드가 그 서버를 통해서만 서로를 찾는데, 서버가 꺼져 있어서 **같은 PC 안의 노드끼리도** 못 찾았습니다.

| 탐색 방식 | 동작 | 조건 |
|---|---|---|
| 기본 (멀티캐스트) | 같은 네트워크에 알리고 서로 찾음 | 같은 `ROS_DOMAIN_ID`, 같은 네트워크 |
| Discovery Server | 정해진 서버에 등록하고 물어봐서 찾음 | 서버가 **켜져 있고 접속 가능해야** 함 |

**해결**

```bash
# 임시 (그 터미널만)
unset ROS_DISCOVERY_SERVER ROS_SUPER_CLIENT
# 영구: 지우지 말고 주석 처리 → 나중에 필요하면 # 만 빼기
sed -i 's/^export ROS_DISCOVERY_SERVER=/# &/; s/^export ROS_SUPER_CLIENT=/# &/' ~/.bashrc
```

**교훈**
- 터미널마다 `unset`하다 하나라도 빠뜨리면 **그 노드만** 안 보임 → 원인 찾기가 매우 어려움
- `ROS_DOMAIN_ID`도 `.bashrc`에 두 번 있었음 → 마지막 값이 적용되므로 팀 PC 모두 같은지 확인

# 2·3. MySQL 초기 설정

```bash
# 상대경로로 다른 폴더에서 실행하면 파일을 못 찾고 아무것도 안 만들어짐
sudo mysql < ~/<워크스페이스>/src/rokey1/db/schema.sql   # 절대경로로

# -p 뒤에 띄어 쓰면 그 값은 비밀번호가 아니라 DB 이름으로 해석됨
mysql -u <user> -p <db>      # 비밀번호 입력 프롬프트 (한/영 확인!)
```

→ 문서의 명령은 모두 **절대경로**로 적기로 함

# 4. DB 연결 공유

HMI 서버에는 HTTP 요청 스레드, 공정 실행 스레드, Action 피드백 콜백 스레드가 동시에 존재합니다.
pymysql 연결은 스레드 안전하지 않아서 패킷 순서가 꼬였습니다 → 쓰기·읽기 전체를 `threading.Lock`으로 감쌌습니다.

# 5·6. colcon 빌드 문제

- ament_python은 `setup.py`의 `find_packages()`로 설치할 폴더를 고르므로 `__init__.py`가 없는 폴더는 **조용히 빠짐**
- 코드를 옮긴 뒤 `install/`에 옛 실행 파일이 남아 테스트가 옛 코드를 import함

```bash
rm -rf build/rokey1 install/rokey1 && colcon build --packages-select rokey1
```

# 7. 인터페이스 불일치

팀원 각자 같은 이름의 `.action`을 따로 정의하다 필드 타입이 달라 통신이 안 됐습니다.
→ 인터페이스 패키지는 **한 곳에서만** 관리하고, 바꿀 때는 팀 전체에 공지해야 합니다.

# 9. "성공"이라는 거짓말

`movel` 등이 도달 불가 지점에서도 성공으로 응답한 사례가 있었습니다.
→ 모든 이동 후 **실제 위치(posx)와 목표 위치를 비교**해 도착을 확인하고, 오차를 task_log에 기록 (예: 도달 불가 gap에서 오차 1643 mm 기록 → `E_MOTION`).
